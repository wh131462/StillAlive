# Release Notes Generator

将版本范围内的完整 Git 变更压缩为一行、面向用户的发布文案。默认只报告结果，不修改文件、不创建标签、不提交或推送代码。

## 工作流

### 1. 确定版本范围

1. 使用用户明确指定的基线标签、目标标签或提交。
2. 用户未指定时，以 `HEAD` 为目标，列出可从目标提交到达的版本标签：

```bash
git tag --merged HEAD --sort=-version:refname
```

3. 优先选择最新的语义化版本标签，例如 `v1.2.3` 或 `1.2.3`，作为基线。
4. 如果目标提交本身已有版本标签，将该标签视为本次版本，选择它之前的最近版本标签作为基线。
5. 不确定哪个标签代表正式版本时，列出候选项并说明歧义，不要静默选取分支、日期或普通里程碑标签。
6. 仓库没有版本标签时，明确说明事实；只有在用户接受后，才使用首个提交到目标提交的范围。

### 2. 读取全部提交

先取得总数和完整主题列表，再查看文件统计：

```bash
git rev-list --count <base>..<target>
git log --format='%h%x09%s' <base>..<target>
git log --format='commit %h %s' --stat <base>..<target>
```

核对 `git log` 中读取到的提交数量与 `git rev-list --count` 一致。不要使用固定的 `-5`、`-10` 或 `-20` 截断历史。

若提交标题含糊、过于技术化或无法判断用户影响，继续读取相应提交：

```bash
git show --stat --oneline <commit>
git show --format=fuller --no-ext-diff <commit> -- <relevant-paths>
```

只读取本地 Git 数据。除非用户要求同步远程，否则不要执行 `fetch`、`pull` 或其他网络操作。

### 3. 提炼用户价值

将提交归并为以下信息，避免逐条复述 commit：

- 新增能力：用户现在能完成的新操作。
- 体验改进：交互、性能、视觉、权限引导和稳定性提升。
- 关键修复：崩溃、数据一致性、安全、更新、构建或发布故障。

优先使用用户能理解的产品语言。内部重构、依赖调整、构建脚本和补丁只有在影响安装、启动、数据、安全或核心功能时才进入文案。

不得根据 `feat`、`fix` 等前缀直接判断重要性；结合文件统计和必要的 diff 判断实际影响。相互关联的提交应合并表达，例如“新增功能 + 后续修复”写成一个完整能力，而不是两条重复描述。

### 4. 生成一行文案

默认输出恰好一行简体中文：

```text
新增……，完善……，优化……，并修复……问题。
```

要求：

- 不加标题、项目符号、版本号、commit hash 或解释。
- 不换行，不使用 Markdown。
- 先写主要新增能力，再写体验优化，最后写关键修复。
- 覆盖版本范围内的重要变更，但不堆砌实现细节。
- 不使用“若干优化”“修复已知问题”等空泛表述，除非提交记录确实无法支持更具体的结论。
- 推荐控制在 60 至 140 个汉字；信息较多时合并同类项，而不是遗漏重要模块。

如果用户要求其他长度、语言、分点格式或应用商店风格，遵循用户格式，同时仍必须读取完整版本范围。

## 输出前检查

- 基线是否是上一个正式版本，而非随意选取的最近提交？
- 是否读取了 `<base>..<target>` 的全部提交且数量一致？
- 是否查看了标题含糊但可能影响用户的提交？
- 是否覆盖主要新增功能、关键体验改进和高影响修复？
- 最终结果是否只有用户要求的一行更新内容？

## 示例

用户请求：`写一行 release 更新内容`

正确行为：先检查版本标签和全部范围提交，再输出类似：

```text
新增断点续传及相机与相册取图能力，完善权限引导和密码本反馈，优化通知同步、定位与移动端交互，并修复 Android WebView 和发布资源问题。
```
