## Context

移动端当前使用 Expo 57、React Native、SQLite 与应用沙盒文件系统。`persons` 仅保存基础资料；`media` 同时服务日记图片和人物头像；备份将数据库快照与全部媒体打包为 ZIP。项目已经使用 `tyme4ts` 展示农历，但尚未接入本地通知模块。

本变更跨越领域类型、SQLite 迁移、文件生命周期、备份、应用状态、人物/设置 UI 和系统通知。实现必须保持本地优先，不把生日、标签或照片发送到外部服务。

## Goals / Non-Goals

**Goals:**

- 用明确且可迁移的数据结构保存阳历或农历生日，并可靠计算下一次生日。
- 提供标准化 MBTI、星座、生肖标签和可管理的自定义文字标签。
- 提供一个人物多个相册、一个相册多张照片的本地文件夹式管理体验。
- 在生日提前 3 天和当天产生可追踪、可重排的本地通知。
- 让新增数据完整参与删除、导出和覆盖恢复。

**Non-Goals:**

- 不实现相册评论、访客、点赞、分享动态、云端上传或多人协作。
- 不实现人脸识别、照片自动分类、EXIF 地点/时间整理或视频相册。
- 不实现跨设备通知同步或服务端推送。
- 不允许修改 MBTI、星座、生肖的标准选项文本；管理仅覆盖体系启停/排序和自定义标签 CRUD。
- 不新增提醒历史、站内消息中心或其他类型的通知。

## Decisions

### 1. 生日保存原始历法字段，不只保存换算后的公历日期

在 `persons` 增加可空字段：`birthday_calendar`（`solar | lunar`）、`birthday_year`、`birthday_month`、`birthday_day`、`birthday_is_leap_month`。生日作为完整出生日期录入，年份不可省略且不能晚于当前日期。

阳历生日直接按月日计算周年；农历生日使用 `tyme4ts` 从原始农历月日逐年换算。农历闰月生日遇到目标年不存在同名闰月时，回退到该月的普通农历月；农历某月没有原始“日”时，使用该月最后一天。这样每年都存在一次可提醒的周年日，且无需维护人工换算表。

替代方案是只存一个公历 `YYYY-MM-DD`。它无法表达“每年按农历过生日”，后续换算会丢失用户意图。

### 2. 星座与生肖是派生标签，MBTI 与自定义标签是显式关联

内置体系定义由代码维护：MBTI 16 项、星座 12 项、生肖 12 项。`person_tag_assignments` 只保存人物选择的 MBTI 和自定义标签；星座、生肖根据生日即时派生，不写入关联表，避免生日修改后出现脏数据。

`tag_definitions` 保存自定义标签，采用规范化文本唯一约束；`tag_system_settings` 保存内置体系的启用状态和显示顺序。停用体系后不再提供新增选择并从人物常规展示中隐藏；MBTI 原选择仍保留，重新启用后恢复。删除自定义标签会先要求确认，并级联移除人物关联。

替代方案是把所有标签都自由文本化。它会产生 MBTI 大小写、星座命名和生肖重复问题，也无法可靠自动派生。

### 3. 相册使用数据库元数据加稳定的沙盒目录

新增 `person_albums`（人物、名称、封面媒体、排序、时间戳）与 `album_media`（相册、媒体、排序、添加时间）表。照片仍复用 `media` 元数据，每张相册照片归属一个相册。物理路径固定为 `people/<personId>/albums/<albumId>/<mediaId>.<ext>`，路径名只使用内部 ID，不使用可改名或含特殊字符的相册名称。

新增照片时先复制到临时文件，校验并计算摘要，再移动到目标目录并提交数据库记录；失败时删除本次临时/目标文件。删除照片、相册或人物时先提交数据库删除，再尽力清理已知文件，并在应用启动时对相册目录执行轻量孤儿清理。相册封面为空时取排序第一张照片。

照片只“复制到应用”，不引用系统照片库原地址，避免用户清理照片库后相册失效。相册名称只影响显示，不触发目录移动。

### 4. 通知采用可重复执行的调度协调器

新增单一 `BirthdayNotificationCoordinator`，根据人物生日、全局开关、提醒时间和当前权限计算未来事件，并与数据库保存的 `birthday_notification_schedules` 映射对账。每个生日产生两类事件：目标日当地时间的提前 3 天提醒和当天提醒；若提前提醒时间已经过去，只安排仍在未来的事件。

协调器在应用完成初始化、回到前台、人物生日变化、人物删除、提醒设置变化和权限变化后运行。它取消失效标识并补齐未来 12 个月的事件；所有日期按设备当前时区重新计算，避免固定 UTC 导致跨日。通知 payload 仅包含内部 personId 和事件类型，标题/正文只显示人物名称与生日提示，不包含其他档案内容。

需要新增 Expo 官方本地通知依赖并更新平台配置。由于项目规则禁止未经明确许可引入依赖，实际实施前必须确认允许加入该依赖；在确认前只可实现无平台副作用的日期计算与存储部分。

替代方案是使用每年重复的系统日历触发器。它无法统一处理农历换算、闰日规则、时区变化和生日编辑后的可靠撤销。

### 5. 通知设置只提供必要的全局控制

设置页增加生日提醒总开关、每日提醒时间、权限状态和前往系统设置入口。默认提醒时间为本地时间 09:00；首次开启时才请求权限，不在启动时打扰用户。拒绝权限不会清除生日或关闭用户意图，界面展示“系统权限未开启”，待授权后重新协调。

本次不增加逐人物提醒开关，避免在人物资料和全局通知状态之间再引入一层配置；如后续有明确需求可单独扩展。

### 6. 备份一次性升级并保持旧备份可恢复

升级备份 schema，快照增加相册、相册媒体、标签定义/关联/体系设置和通知偏好；通知系统生成的系统 identifier 不导出。导出时保留 `people/<personId>/albums/...` 的相对路径，恢复时重建新的本地绝对路径并在事务中恢复关系。

旧 schema 备份通过显式迁移补齐空集合和默认设置后恢复；新 schema 的完整性校验必须拒绝悬空人物、相册、媒体或标签关联。通知在恢复完成后按当前设备权限重新生成。

## Risks / Trade-offs

- **农历闰月的生日习惯因人而异** → 本设计采用“无闰月则普通月”的确定性规则，并在农历生日编辑说明中展示该规则。
- **大量人物可能产生较多待处理通知** → 仅维护未来 12 个月且在每次协调时对账；调度失败必须记录并在设置页提示，不静默宣称成功。
- **数据库与文件系统无法组成同一事务** → 使用临时文件、确定的操作顺序、失败补偿和启动时孤儿清理。
- **删除自定义标签会影响多个人物** → 删除确认展示受影响人物数量，数据库外键级联保证一致性。
- **停用标签体系可能让已录入值暂时不可见** → 数据保留，并在设置页明确“停用仅隐藏，不删除人物已有数据”。
- **本地通知依赖尚未安装** → 实施前单独确认依赖变更，并通过真机验证权限和调度；静态构建不能替代真机验收。

## Migration Plan

1. 增加领域类型和纯函数：生日校验/周年计算/派生标签，并先用现有类型检查验证。
2. 增加 SQLite 版本迁移、表和 repository API；旧人物生日默认为空，内置标签体系默认启用。
3. 扩展备份 schema、旧版迁移、关系校验和相册文件物化。
4. 实现标签设置、人物生日/标签编辑及详情展示。
5. 实现相册路由、文件操作与删除补偿。
6. 经依赖许可后接入本地通知、平台配置、调度协调器和设置 UI。
7. 执行 lint/typecheck/build；在 iOS/Android 真机验证照片权限、通知权限、时区变化、农历生日和备份往返。

回滚时先发布关闭生日通知的版本并取消本应用已登记的生日通知，再回退 UI。数据库新增列/表保留不删除，避免破坏性降级；旧代码会忽略这些数据。
