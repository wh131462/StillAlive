## Context

经过 `vibrant-design-refresh`（视觉系统）+ `interactive-prototypes`（多屏可交互原型）+ `chronicle-pivot`（产品定位 pivot）三次迭代后，整体形态已经成型，但是用户复看时反馈三点：

1. **交互流程偏技术**：屏切换器编号 chip、Markdown 工具栏、@ 候选列表、备份页 WebDAV/S3 字眼——整体像开发者工具。
2. **主页心流不顺序**：「✓ 我还在」与「写一条」并列展示，两者关系不直觉；用户进来就能写，缺少"先确认存在再考虑表达"的节奏。
3. **人物模块缺少叙事**：列表 + 详情的结构没有体现"我和身边人之间的网络"；详情字段固定，无法表达个人化的关注点；事件无法支持模糊时间。

约束：

- 仅修改 `docs/design/` 与 `docs/PRD.md`；不引入新依赖。
- vibrant 设计 token 0 改动。
- 关系图必须用原生 SVG / 静态布局（无 d3 / cytoscape / vis.js）。
- 备份功能契约不变，仅 UI 文案与流程改造。
- 不影响后端账号鉴权与可选邮件中转。

## Goals / Non-Goals

**Goals:**

- 主页改为三态状态机：未打卡仅看到打卡按钮 → 已打卡后才出现写入入口 → 写过后折叠为小条。
- 人物 tab 默认进「以我为中心」的关系图，列表降为副视图。
- 人物详情升级为：固定字段 + 自定义键值对 + 事件流（模糊时间 + 拖拽排序 + 归属规则）。
- 关系类型支持完全自定义 + 常见预设。
- 备份 UI 全面去技术化：JSON / 数据库文件导出 / 导入为主；云同步为次级；术语全部本地化。
- 屏切换器砍掉编号 chip，改为简洁标签条。
- Post Composer 改为底部 sheet 上拉，不再独立屏。

**Non-Goals:**

- 不实现真正的本地存储 / 同步逻辑（spec 已固化，原型 mock 即可）。
- 不实现真正的关系图布局算法（用预置坐标 mock）。
- 不实现真正的拖拽排序（用静态 DOM 顺序模拟）。
- 不实现暗色模式、无障碍专项。
- 不引入任何前端框架 / 构建工具 / CDN 脚本。

## Decisions

### 决策 1：主页状态机用三态卡片变形而非三屏切换

**选择：** 主页打卡卡片有 `.is-pending / .is-done / .is-collapsed` 三种状态，通过 class 切换实现，使用弹簧曲线变形。整个主页不需要跳屏。

**为什么？**

- 苹果家庭 app / 健康 app 都是这种"同一卡片在不同状态下变形"的设计语言，符合用户对 iOS 的直觉。
- 状态间的过渡用动效连接，让用户感受到"我点了一下，世界响应了"，而不是"我点了一下，跳了一屏"。

**替代方案：**

- 方案 A（已选）：单页三态卡片
- 方案 B：分三个 tab / 屏。割裂感强，每次进入需要重新理解
- 方案 C：未打卡时是大全屏，打卡后缩为顶部小条。视觉跳跃过大

### 决策 2：人物 tab 默认进关系图

**选择：** 人物 tab 进入即看到关系图（以"我"为固定中心），顶部 `.segmented` 控件可切换到列表视图。用户的偏好被本地记住。

**为什么？**

- 列表是工具感，图是叙事感——「这是我和我身边的人」一眼可见
- 苹果家庭 app 的房间视图是类似设计，证明在移动端可用
- 列表作为副视图保留，重度用户（人物 50+）仍可走列表

**替代方案：**

- 方案 A（已选）：默认图，副选列表
- 方案 B：图 / 列表并列两 tab。决策疲劳，用户每次进入要选
- 方案 C：只有图。当人物 50+ 时图视图会拥挤；列表是合理 fallback

### 决策 3：以"我"为固定中心而非平等节点

**选择：** 「我」节点固定在画布几何中心，缩放与平移以我为锚。其它人物围绕我布局。

**为什么？**

- 用户的心智模型本就是"我和我身边的人"
- 苹果家庭 app 没有中心，但那是"家"作为容器；本产品没有"家"这个容器，"我"自然成为锚
- 新用户进入不迷路："那个最中间的就是我"

**替代方案：**

- 方案 A（已选）：固定中心
- 方案 B：力布局无中心。需要算法（力学模拟）+ 第三方库或自实现，违反"零依赖"约束
- 方案 C：用户首次选中心。多一步决策

### 决策 4：关系类型预设 + 完全自定义

**选择：** 预设至少 25 种常见关系（家人 + 社会双分组），同时支持用户自由输入自定义类型（最长 8 字），自定义类型加入本地词典持续可用。

**为什么？**

- 你提到「想加些常见关系预设」，所以预设是必要的
- 但你也说「可以自定义很多类」，所以不能限定预设
- 8 字上限保证视觉一致性（关系标签放在节点连线中点，过长会破坏图）

**替代方案：**

- 方案 A（已选）：预设 + 自由自定义
- 方案 B：固定枚举不可自定义。被你否决
- 方案 C：完全自定义不提供预设。新用户成本高

### 决策 5：事件 timeHint 为自由字符串 + sortKey 用户拖拽

**选择：** Event 的时间表达分两层：
- `timeHint`: 自由字符串（"高三那年" / "2018-06" / "2018 暑假" / "童年"皆可）
- `sortKey`: 数字，由用户拖拽排序产生（不依赖真实日期）

**为什么？**

- 你明确说"允许模糊记录时间 但是可以排序"
- 自由字符串保留情感记忆（"高三那年"比 "2007-09 ~ 2008-06" 更真实）
- 拖拽产生的 sortKey 解决排序问题，不强迫用户写出真实日期

**替代方案（见 spec ADDED Requirements 已说明，B 选中）**

### 决策 6：事件归属"参与者"

**选择：** 事件归属由 `participants` 数组决定。

- `participants` 含 'self' → 出现在我的主页历史合流 + 该人物的事件流
- `participants` 不含 'self' → **仅**出现在该人物的事件流（如"妈妈年轻时去过西藏"）

**为什么？**

- 你明确说"如果是我在记录里写了 那当然 我自己也可以看到 只是想强调一些 非我参与的事情 要只归属人物"
- 这条规则非常自然，符合"事件是关于谁的"的直觉

### 决策 7：备份去技术化是 UI 改造，契约不变

**选择：** 底层备份契约（manifest.json / data.json / media/ / 加密算法）保持 `chronicle-pivot` 的设计；只改 UI 文案、流程顺序、术语命名。

**为什么？**

- 契约不变意味着已有备份包仍可被新版本读取
- UI 文案改造代价小、收益大
- 给后续开发自由：仍可以在底层使用 WebDAV / S3 / AES-256-GCM，但用户不需要懂这些

**改造要点：**

| 改造前 | 改造后 |
|--------|--------|
| WebDAV | 网盘服务（下拉里包含坚果云 / Nextcloud） |
| 服务器地址 | 网盘地址 |
| 应用密码 | 密码（小字"建议用应用专用密码"） |
| accessKeyId / secretAccessKey | 不暴露 |
| AES-256-GCM | 上传前加密保护 |
| 测试连接 | 测试一下 |
| 失败原因（HTTP 状态码） | 「地址写错了？」「账号或密码不对？」 |

### 决策 8：写入入口仅通过底部 sheet

**选择：** Post Composer 从独立屏改为底部上拉 sheet（移动端）/ 居中浮层（桌面端）。

**为什么？**

- 上拉 sheet 是 iOS 标准范式（备忘录、信息、Twitter 等都用）
- sheet 让用户保持对底层（主页 / 时间线）的视觉连接，写完直接看到回到的位置
- 减少屏切换，符合"少跳页"的苹果原则

**约束：**

- sheet 不能塞太多——只放 textarea + 4 个圆形小图标（@ / 📷 / ⏰ / 完成）
- "Markdown / 保存草稿 / 自动保存于"等技术化字眼全部砍掉

## Risks / Trade-offs

- **风险：关系图在节点超过 30 时会拥挤** → 视觉密度高难以辨识
  - **缓解**：用户可拖动节点重新布局；提供「按关系类型筛选」chip；50+ 时建议切到列表

- **风险：自由 timeHint 字符串无法做时间筛选** → 用户想"看 2020 年发生过什么"时无法查
  - **缓解**：当前 MVP 范围内放弃这个能力；后续若加智能识别（parser 把"高三那年"解释为 2007 年区间）再说

- **风险：状态机隐藏写入按钮可能让用户迷失** → 第一次打开看不到"写一条"按钮
  - **缓解**：未打卡卡片下方加引导小字"先打个卡，再聊点什么"；动效让"点完打卡 → 出现写入按钮"的因果关系清楚

- **风险：去技术化的备份 UI 反而让进阶用户感到信息不足** → 不知道实际用什么协议
  - **缓解**：高级用户可在"设置 → 关于"看到「技术细节」折叠区，里面列出 WebDAV / S3 / 加密算法等

- **权衡：sheet 不能放太多内容 → @ 候选无法看到所有人**
  - **接受**：sheet 内 @ 弹出二级 sheet 选人，符合 iOS Files / Contacts 选人范式

## Open Questions

- 关系图布局：MVP 用预置坐标 mock，后续真前端实现时用什么布局算法？倾向先用同心圆按关系类型分层，5 圈足够。力学布局留给后续。
- 自定义关系类型的去重：用户输入"妈妈"已存在时是否复用？倾向自动去重（trim + case-insensitive）。
- 事件流的「分页」：当某人物事件超过 20 条时如何呈现？倾向不分页，无限滚动 + 顶部年份索引。
- Post 自动询问"记为某人经历"的 toast 频率：每次都问还是仅首次？倾向**仅当 Post 含 @ 时才问，每次都问但有"以后别问"按钮**。
