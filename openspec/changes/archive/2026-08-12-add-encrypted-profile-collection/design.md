## Context

移动端当前使用 Expo 57、Expo Router、SQLite、SecureStore 与本地 AES-256-GCM；人物资料和标签均只保存在设备中。现有 Portal 是由 GitHub Actions 发布到 GitHub Pages 的纯静态站点，并且生产配置已声明 `stillalive://` 自定义协议。

本变更需要在不增加 API、数据库服务或第三方表单服务的前提下，让另一个人填写少量人物资料，再通过现有聊天或分享渠道把结果交回创建邀请的设备。GitHub Pages 只负责分发表单代码和承接 HTTPS 链接，不能成为数据存储或可信执行环境。

## Goals / Non-Goals

**Goals:**

- 创建与某个本地人物绑定、可过期、成功导入后不可重复使用的一次性邀请。
- 只允许填写姓名、性别、生日、MBTI 和邀请中列出的现有自定义标签。
- 使用非对称密钥交换，使邀请只暴露公钥，响应只能由持有对应私钥的 App 解密。
- 让填写、加密和响应链接生成全部发生在浏览器本地。
- 在 App 中逐字段预览差异，明确确认后才修改人物资料。
- 为自定义协议拉起失败提供复制响应码并在 App 内粘贴导入的回退路径。

**Non-Goals:**

- 不收集头像、图片、附件、长文本、自定义问题、关系、印象或生日提醒设置。
- 不提供服务器端提交记录、状态查询、撤回、提醒或多设备同步。
- 不验证填写者的真实身份；持有邀请链接的人均可生成响应。
- 不让静态页面直接访问 App 的 SQLite、SecureStore 或其他本地数据。

## Decisions

### 1. 使用“邀请链接 → 加密响应链接 → App 导入”的离线协议

App 创建邀请时生成随机 `requestId`，并在本地保存目标 `personId`、允许字段、标签选项映射、过期时间和状态。分享链接使用 `https://<portal>/collect/#request=<base64url>`；请求描述放在 URL fragment 中，不作为 HTTP 查询参数发送给 GitHub Pages。

浏览器完成填写后生成 `https://<portal>/receive/#response=<base64url>`。填写者通过系统分享把该 HTTPS 链接发送回来；所有者打开后，由中转页通过用户操作尝试拉起 `stillalive:///profile-collection/import?response=...`。如果平台阻止自定义协议或消息软件截断协议链接，中转页显示复制入口。App 的同一解析器接受完整 HTTPS 响应链接、自定义协议链接和纯响应码，三种输入进入完全相同的验证、解密和审核流程。

替代方案是让提交按钮直接打开 App。它只会打开填写者设备上的 App，无法把数据传到邀请创建者设备，因此不解决跨设备回传问题。

### 2. 每个邀请使用独立 P-256 ECDH 密钥对

创建邀请的 App 为每个请求生成独立 P-256 私钥和公钥。私钥以 `requestId` 为索引保存到 SecureStore，不写入邀请、不进入备份；邀请只包含未压缩 P-256 公钥。

静态页面使用浏览器 Web Crypto 生成临时 P-256 密钥对，与邀请公钥执行 ECDH。双方将共享点规范化为 32 字节 X 坐标，再使用 HKDF-SHA-256 派生一次性 AES-256-GCM 密钥。响应包含临时公钥、随机 HKDF salt、随机 GCM nonce、密文和认证标签，不包含共享密钥或明文。

移动端复用项目已有的 `@expo/dom-webview`，通过仅在本机运行的隐藏 DOM 加密组件调用 Web Crypto 完成 P-256、HKDF 和 AES-GCM；Portal 使用同一套浏览器原生算法。私钥以 JWK 文本从本机 DOM 组件返回 React Native 后立即写入 SecureStore，解密时短暂传回本机 DOM 组件，不经过网络或持久化网页存储。选择 P-256 而不是 RSA，是为了保持密钥和响应体较小；选择现有 DOM Web Crypto，而不是手写曲线算法或引入远程脚本，是为了避免密码学实现风险和运行时供应链变化。

协议使用显式版本号。HKDF info 与 AES-GCM additional authenticated data 均包含固定协议标识、版本和 `requestId`，防止响应跨请求替换。App 必须拒绝无效曲线点、非规范编码、认证失败、未知版本和超长载荷。

### 3. 邀请不携带本地人物 ID 或当前资料值

公开请求描述仅包含协议版本、随机 `requestId`、过期时间、公钥、允许字段以及表单所需的枚举选项。`personId` 与已有字段值只保存在创建邀请的设备中。

自定义标签不能直接暴露本地标签 ID。App 为邀请中的每个标签生成请求内临时选项 ID，并在本地待处理记录中保存临时 ID 到真实标签 ID 的映射。响应只能返回邀请内提供的临时选项 ID，不能创建新标签。

这减少了邀请链接携带的本地标识和人物资料，也避免响应伪造任意标签关联。

### 4. 响应使用受限的版本化 JSON

加密明文采用 UTF-8 JSON，包含 `version`、`requestId`、提交时间和 `answers`。允许的答案为：最长 40 字的非空姓名、既有性别枚举、完整阳历或农历生日、标准 MBTI 值，以及邀请内标签临时 ID 的集合。

浏览器先按请求描述校验；App 解密后必须使用本地领域规则再次校验，不能信任静态页面。生日响应只改变历法和日期，保留人物已有提醒偏好；人物原本没有生日时使用当前 App 的默认提醒语义。空值表示“未回答”，不表示清除原字段。

为降低深链接和消息分享截断风险，表单不接受自由长文本，并对请求描述、密文信封和解密后 JSON 设置固定字节上限。具体上限由实现通过 iOS/Android 真机验证后固化，但必须覆盖本变更允许的全部字段。

### 5. 导入采用逐字段审核，成功确认后才消费请求

App 收到响应后先根据 `requestId` 查找本地待处理记录和私钥，检查请求未过期、未消费且目标人物仍存在，再解密并验证内容。导入页以当前本地值为基准展示每个变化字段，默认不直接写入；使用者可以逐项取消，最后确认一次性保存。

仅在人物和标签更新成功提交后，将请求标记为已消费并删除私钥。解密失败、用户取消或保存失败均不得消费请求。已消费、过期、未知或私钥丢失的请求显示明确错误，不允许降级为未验证导入。

替代方案是响应解密成功后自动覆盖。它会让误填、旧响应或转发给错误对象的数据直接破坏本地资料，因此不采用。

### 6. 待处理邀请是临时本地状态，不进入备份

SQLite 新增待处理邀请元数据表，SecureStore 保存对应私钥。导出和恢复不包含这些记录；应用恢复、重装或清除安全存储后，旧响应可能无法解密。App 在创建邀请、打开导入页和回到前台时清理已过期请求及其私钥。

首版假设邀请固定 7 天过期，以避免增加额外设置界面。若产品需要自定义有效期，应在实施前修改规格，而不是在实现中隐式增加配置。

## Risks / Trade-offs

- **邀请被转发后，其他人也能填写** → App 仅保证响应机密性与完整性，不宣称验证填写者身份；导入前必须人工审核。
- **浏览器不支持所需 Web Crypto 能力** → 页面在展示表单前执行能力检测，不支持时停止填写并提示更换现代浏览器。
- **消息软件或平台截断长链接** → 严格限制字段和载荷大小，并提供响应码复制/粘贴回退；真机验证后确定字节上限。
- **私钥因重装、清理或 SecureStore 异常丢失** → 明确提示响应不可恢复，不把私钥上传或加入备份来换取可恢复性。
- **自定义协议可能被其他 App 抢占** → 深链接只携带密文；真正解密仍要求本机 SecureStore 私钥。后续可单独升级为 Universal Links/App Links。
- **Portal 代码可被任何人查看** → 安全性只依赖标准密码学与私钥保密，不依赖隐藏前端代码。
- **App DOM WebView 不提供所需 Web Crypto 能力** → 加密组件先执行能力检测并返回明确错误；用真机验证 iOS/Android WebView 的 P-256、HKDF 和 AES-GCM 支持。
- **P-256 两端实现细节不一致** → 用固定测试向量验证公钥编码、共享密钥、HKDF、AAD 和 AES-GCM 互操作，再接入界面。

## Migration Plan

1. 定义版本化邀请/响应协议、字段校验和固定互操作测试向量。
2. 新增移动端 DOM Web Crypto 桥接、密钥生命周期、SQLite 迁移和 SecureStore 适配。
3. 在 Portal 增加静态填写、加密、分享及响应中转页面。
4. 在人物详情增加邀请创建入口，在 App 增加深链接解析、粘贴回退和审核导入页。
5. 执行类型检查、Portal 构建和协议测试，并在 iOS/Android 真机验证分享、冷/热启动、过期与长度边界。

回滚时先隐藏邀请创建入口并停止生成新协议链接；保留数据库表不会影响旧版本业务数据。已有待处理邀请在回滚版本中不可导入，重新升级后仍可在未过期且 SecureStore 私钥存在时处理。

## Open Questions
