## Context

人物数据目前主要保存在 `persons` 表及人物与 Post、相册、音乐、书籍的关联表中。人物详情页能够展示固定资料和关联记录，但没有独立的经历实体、可扩展字段、非生日日期、隐私展示状态或合并操作。应用是 Expo React Native + SQLite 的本地优先架构，已有数据库版本迁移、统一 AppState、备份快照和 `DraggableBottomSheet` 交互模式。

## Goals / Non-Goals

**Goals:**

- 让人物拥有独立、可排序、可置顶的事件记录，并允许自由格式时间。
- 让人物资料可由用户按需扩展，同时保留固定字段的简单编辑体验。
- 让重要日期与现有生日提醒共存，并支持年度提醒。
- 让隐私状态在人物详情中可见、可切换，默认不影响本地历史数据保存。
- 让合并操作在单个 SQLite 事务中迁移所有现有关联，避免半合并状态。
- 让新字段支持旧数据库、旧备份和缺失字段的向后兼容。

**Non-Goals:**

- 本次不实现云端同步、端到端加密或系统通讯录同步。
- 本次不实现自动识别重复人物；由用户在人物页明确选择主人物和待合并人物。
- 本次不改变既有 Post 编辑器和主页时间线的基础排序规则。

## Decisions

- **事件使用独立表，参与人使用 JSON。** `person_events` 保存事件自身的标题、描述、模糊时间、置顶和排序字段；`participant_ids_json` 保存人物 ID 列表。这样事件可独立查询和合并迁移，又不为当前轻量场景引入额外关联表。替代方案是把事件整体 JSON 放进 `persons`，但不利于筛选、排序和备份增量。
- **自定义字段和重要日期使用 JSON 列。** 两者都是人物拥有的轻量字符串集合，放在 `persons.custom_fields_json` 与 `persons.important_dates_json` 中，减少表数量和迁移风险。键和值在应用层限制长度并去重。
- **隐私使用枚举状态而非删除/加密。** `privacy_mode` 取 `normal` 或 `private`。详情页默认隐藏联系方式、自定义字段和重要日期，并提供本页一次性显示开关；历史 Post、相册和收藏关系不删除。真正的加密存储作为后续独立变更。
- **合并由 repository 事务完成。** 目标人物保留其已有资料，空字段从源人物补齐；数组字段去重合并；Post、相册、人物音乐/书籍、标签、事件和关系节点迁移到目标人物；源人物的引用关系全部处理后删除源人物。冲突字段不自动覆盖，由合并前预览展示。
- **时间线筛选在详情页内存完成。** 事件数量属于单个人物范围，详情页将关联 Post 与事件映射为统一条目，提供“全部 / 记录 / 经历”筛选、按日期或模糊时间分组、置顶优先。若数据量增长，再下沉为 repository 查询。
- **继续复用现有交互。** 类型选择、编辑和确认使用现有 sheet、统一 `feedback` 和主题 token，不引入第三方选择器或通知依赖。

## Risks / Trade-offs

- [JSON 字段查询能力弱] → 仅在单人物详情页解析；保存时校验结构，备份直接保留原始对象。
- [合并涉及多种外键和文件引用] → 所有数据库引用在一个事务中处理，媒体文件只在确认无引用后清理。
- [隐私开关不是加密] → 文案明确为“隐藏展示”，不宣称安全隔离；真正加密另立需求。
- [大量事件导致详情页渲染变慢] → 初期限制单条事件长度并使用 `FlatList`/分组映射，保留后续分页入口。

## Migration Plan

1. 在数据库版本迁移中增加人物 JSON 列和 `person_events` 表，旧人物默认空数组、普通隐私状态。
2. 扩展 types、mapper、repository、AppState 和备份快照；旧备份缺少新字段时使用默认值。
3. 先上线人物编辑与详情展示，再启用事件筛选、置顶、日期提醒和合并入口。
4. 若出现问题，可回滚 UI 代码；数据库新增列和表保持向后兼容，不删除旧字段。

## Open Questions

- 重要日期的通知是否需要单独的系统通知文案和通知开关，还是只在人物页展示？本次默认支持页面展示和年度提醒配置，不扩展现有通知调度器。
- 隐私人物是否需要在人物列表中整体隐藏？本次默认仍显示人物姓名和“已隐藏资料”标记，避免用户找不到人物。
